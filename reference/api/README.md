## What changed in 3.12.0 (Phase 29A)

**Additive.** Two fields on `ProductDetail`, both resolved Item Price facts, and
both reaching the client through the calls that already exist — `get_item` and
`resolve_variant`. Nothing is fetched separately.

* `mrp: number | null` — **informational display only**. Not a base price, rate,
  discount or total; nothing is derived from it on either side. It is *not*
  validated against the selling rate and may legitimately be lower, so a computed
  "saving" would sometimes be negative. Blank, zero and negative all arrive as
  `null`.
* `quantity_control: { moq, quantity_multiplier, allowed }` — quantity-input
  **guidance**, and **never enforced by the backend**: cart, checkout and Sales
  Order accept exactly the quantities they accepted before. The multiplier is a
  step counted FROM the start — `moq 10` with multiplier `6` offers 10, 16, 22,
  not multiples of six — and is unrelated to UOM, conversion factor and pack size.

`allowed` is `false` when the pricing preview applied a Pricing Rule, because a
rule may change behaviour at a quantity threshold. The two values are a **pair**
governed by that one flag: when it is false, both are ignored and the ordinary
quantity input returns. It describes the current preview quantity only — nothing
may predict whether a rule would activate at some other quantity.

Neither field appears on `ListingCard`, `ProductSuggestion` or the nested
`pricing` object.

## What changed in 3.11.0 (Phase 28C)

**Additive, and one enum value.** `Destination.type` gains `all_products`.

A merchant who wanted a menu item pointing at `/products` previously had to pick
`External URL` and type the route by hand. That still works and is still
supported; `All Products` is simply the tidier way to express it.

```jsonc
{"type":"all_products","target":null,"href":"/products",
 "external":false,"open_in_new_tab":false}
```

Like `home` and `catalog` it is a **fixed route**: `target` is null and `href` is
backend-owned and always exactly `/products`, so there is no merchant input to
mistype and nothing for the client to validate. The visible menu text stays the
merchant's own `label` — never render the type name.

**Angular needed no navigation change.** Routing already reads `href` and
`external` rather than switching on `type`, so the new value only had to be added
to `MenuDestinationType`.

## What changed in 3.10.0 (Phase 28A)

Catalogue-wide browsing, behind the new `/products` page.

* `catalog.get_items` — **`scope_value` is now optional**. Omit it and the listing
  browses the whole public catalogue instead of one category. Only the SCOPE
  changes: same eligibility, same pricing, same sort, same cursor, same response
  shape. `scope_type` is unaffected, and `all`/`collection` remain reserved words
  that answer `unsupported_scope`.
* `catalog.get_browse_categories` — **new**. Every enabled, slugged, listable
  category, FLAT, at every depth. Each row is a valid `scope_value` target, so a
  chip drawn from it cannot answer `category_not_listable`. Metadata only — no
  items, no prices — and **no synthetic `All` row**: that option is the absence of
  a scope, so the storefront adds it client-side.
* Merchandising filters stay category-only. A `storefront_filters` selection sent
  without `scope_value` answers `storefront_filter_context_required`, and the
  scope is part of the cursor binding — a catalogue-wide cursor replayed against a
  category answers `cursor_invalid`.
* The destination projector resolves a merchant `External URL` of `/products` to
  `external: false`. **Follow the `external` boolean, never the machine `type`**,
  which still reads `external_url`.

## What changed in 3.9.1 (Phase 27B, corrected)

A contract correction with **no runtime change**: `get_item` and `resolve_variant`
return exactly what they returned in 3.9.0.

3.9.0 added `gallery`/`sections` directly to `ProductDetail` — which is also the
schema `resolve_variant` answers with. One schema was doing two jobs, so the
document promised merchandising back from a variant selection that deliberately
never sends it. 3.9.1 splits the two apart:

```text
ProductDetail          resolved SKU detail          -- NO merchandising
ProductMerchandising   { gallery, sections }        -- both required
ProductPageDetail      allOf: ProductDetail + ProductMerchandising
VariantFamily          allOf: family fields + ProductMerchandising

get_item         -> oneOf [ ProductPageDetail, VariantFamily ]
resolve_variant  -> ProductDetail
```

So a product page — simple or family — always carries both arrays, and a resolved
variant carries neither. **Selecting a size changes the SKU, price, UOM and stock
and must not reload or replace the gallery or the content**, because merchandising
belongs to the public product entity: the simple Item, or the template for a whole
family.

## What 3.9.0 introduced (Phase 27B)

* `catalog.get_item` — additive `gallery[]` and `sections[]` on **both** branches.
  A product page's merchandising arrives with the product; there is no second
  request.
* `ProductGalleryImage` — `image`, `alt_text`, `caption`, `is_primary`. Array
  order is authoritative, and `Item.image` is never synthesised into a row: an
  empty gallery is `[]`, and the caller falls back to `image` itself.
* `ProductContentSection` — `title` + ordered `blocks`. The section title is the
  merchant's grouping and is independent of what the blocks inside it are.
* `ProductContentBlock` — a **new** six-type union (`rich_text`, `key_value`,
  `table`, `image`, `download`, `video`), discriminated on `type`. It is *not*
  the Phase 25 CMS `ContentBlock`: `rich_text` and `image` exist in both unions
  with different shapes, and the two must never be merged.
* `catalog.get_product_suggestions` — unchanged, still its five lightweight
  fields.

These shapes are untouched by 3.9.1; only where they attach changed.

## What changed in 3.4.0 (Phase 25C)

* `cms.get_menu` — **new**. Published navigation tree, max two levels, with
  normalised destinations (type + public slug, never a database id).
* `cms.get_page` — **new**. A published page as ordered, discriminated blocks.
  Contains customer-priced Product Grid cards: **never cache across users**.
* `catalog.get_category_filters` — **new**. Facets for a category, from that
  category's own Filter Set only. No counts.
* `catalog.get_items` — additive `storefront_filters` parameter: OR within a
  filter, AND across filters, and part of the cursor binding.

## What changed in 3.3.0 (Phase 23B-5U / 24B / 24D-1)

* `catalog.resolve_variant` — **new**. `GET`, `template` + JSON-encoded
  `attributes` + `qty`; returns the shared product-detail payload.
* `catalog.get_item` — two discriminated modes (`is_template` 0 or 1); a family
  carries `attributes[]` + `variants[]` and no price.
* `catalog.get_items` — published for the first time (it shipped in Phase 22B);
  one card per simple Item and one per family, with `has_variants` and
  `price_state`.
* `cart.add_to_cart` — documents the server-side SKU revalidation and its
  refusals (`item_is_template`, `item_not_purchasable`, `item_not_found`).
* Selling UOM fields (`uom`, `stock_uom`, `conversion_factor`, `stock_qty`) on
  every priced payload.

**Valid variant combinations come only from `variants[]`.** Attribute values are
global in ERPNext, so a cross-product of `attributes[].values` invents
combinations nobody can buy. Never construct an item code in the browser.

A backend test (`test_response_contract.TestPublishedApiReference`) fails if a
whitelisted endpoint or a published error code is missing from this package.
